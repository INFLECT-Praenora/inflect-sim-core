Dynamic Coupling — bidirectional co-simulation and physiological intervention

Q Can the simulation core run a genuine co-simulation — two processes that exchange state on every tick inside one composite — rather than running engines in parallel and comparing them afterwards (studies 01/02) or as parallel tiers (study 03)?

Claim

The `sepsis_cosim` composite couples two process-bigraph processes that exchange state every tick. The Tellurium sepsis physiology engine writes its global parameters (pathogen, hemodynamics) to a shared store. An antibiotic-PK controller process reads the pathogen, integrates a one-compartment drug PK, and writes the drug-killed pathogen back into the engine through its `parameters_in` port before the engine's next step. The treatment the controller computes at tick n changes the physiology the engine integrates at tick n+1 — a real feedback loop, not two independent runs. With the controller enabled (closed-loop antibiotic), bacteremia is cleared. With it disabled (treat=False, the matched control from the same composite), bacteremia climbs. The pathogen drives septic collapse, so the loop removes the cause. The multi-day clinical endpoint itself (studies 03/05) is beyond this run's horizon.

Background

Question Can the simulation core run a genuine co-simulation — two processes that exchange state on every tick inside one composite — rather than running engines in parallel and comparing them afterwards (studies 01/02) or as parallel tiers (study 03)?

Model & approach

Demonstrate the co-simulation pillar with a clinically meaningful instance: couple the real BioGears-sepsis physiology engine (Tellurium) to a closed-loop antibiotic controller process in one composite, with a feedback edge, and show the loop acting on the physiology in flight. Run a matched untreated control from the identical composite (controller disabled).

Why: The main claim is a capability claim, and it is fully supported: two process-bigraph processes run in one composite and exchange state every tick through shared stores, with a genuine feedback edge (the controller's writeback at tick n is the engine's input at tick n+1). That is what sets co-simulation apart from the parallel engine comparison of studies 01/02 (same spec under different engines, compared after the fact) and from the parallel surrogate tier of study 03. The clinical instance — a closed-loop antibiotic that senses bacteremia and doses against it — is chosen so the coupling does something legible: the controller clears the pathogen that the matched untreated control (the identical composite with the controller disabled) lets climb. This study does not claim a validated clinical outcome. The pathogen is the upstream driver of the sepsis cascade (inflammation -> vasodilation -> hypotension), so clearing it removes the cause of collapse, but the collapse itself unfolds over 37-72 h (studies 03/05), and the exact engine is too slow to integrate matched treated/untreated arms to that endpoint in this pass. So the honest reading is: the co-simulation capability is demonstrated end to end on the real model, and the treatment's effect on its direct target (bacteremia) is shown; the downstream multi-day endpoint is referenced from the committed severity studies, not re-derived here. The controller's PK is an illustrative Emax/one-compartment model, not a calibrated pharmacology. Swapping it for a COPASI/Tellurium PK engine (true heterogeneous engine-to-engine co-simulation) is a noted follow-up.
